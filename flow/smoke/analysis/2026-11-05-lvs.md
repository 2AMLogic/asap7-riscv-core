# LVS mismatch on the 2026-11-05 counter smoke layout: 19 topology errors, by cause

`flow/smoke/records/2026-11-05/lvs.json` reports `status: "mismatch"` with
`error_count: 19` (`category_error_counts: {"topology": 19}`) and
`mismatch_count: 76`, comparing the routed placeholder counter against the
as-built gate-level netlist from the same place-and-route run. This file
classifies every one of the 19 errors by cause, measures the suspected cause,
and states what the record's `power_connectivity` verdict means for the
evidence tiers.

**This is layout, LVS and timing-adjacent evidence only, against a predictive
PDK.** ASAP7 is not a foundry process and this block is never fabricated.
Every number below is a tool result against a predictive model, a pinned rule
deck and a pinned tool release — nothing is a measurement, and nothing here
says anything about silicon.

**The record is not changed by this analysis.**
`flow/smoke/records/2026-11-05/` is append-only evidence; nothing in it was
rewritten, no flow setting was altered, and no probe wrote inside the repo
(all probe artifacts lived in `/tmp` and were deleted with it). See "What was
deliberately not done" at the end.

## Reproduction

The committed verdict reproduces exactly from the committed inputs and the
pinned tool, outside the repo. The request file was rebuilt with the shape
`flow/smoke/run.sh:323-326` emits (same layout, same reference, same
`options.finfet_bulk`; the CDL fetched at the pinned cell-library commit and
verified against the record's `cell_cdl` hash before use):

```bash
# probe 1 — the record's own request shape
uvx --from "klayout-tools==0.9.0" klt lvs probe1.req.json --format json
```

Result at klt 0.9.0: `status: "mismatch"`, `error_count: 19`,
`mismatch_count: 76`, `category_counts` identical to the record
(36 / 18 / 2 / 1 / 19), `counts` identical (0 / 418 / 0 devices, 47 / 230 / 0
nets, 2 / 11 / 0 pins) — and the report echoes
`options.flatten_reference: true`, `options.flatten_layout: false`, although
the request set **neither** flatten option. That echo is the pinned tool's own
default on this route, self-evidenced by the record itself; the pinned klt's
`docs/cli/lvs.md` ("Gate-level Verilog references on a FinFET deck") states
the same defaults and names the flattened recipe as the supported path. Exit
code 3 (klt's mismatch exit).

```bash
# probe 2 — the same request plus the documented recipe
#   "options": {"finfet_bulk": {...}, "flatten_layout": true, "flatten_reference": true}
uvx --from "klayout-tools==0.9.0" klt lvs probe2.req.json --format json
```

Result at klt 0.9.0, run exactly once: **`status: "match"`, `error_count: 0`,
exit 0** — 418/418 devices matched, 230/230 nets matched. The documented
recipe completes on this block; it does **not** reproduce the SIGSEGV of
klayout-tools [#5630](https://github.com/2AMLogic/klayout-tools/issues/5630)
(open; ~1070-instance block at v0.9.1). A datapoint comment with these sizes
was posted there. The one-variable flip from probe 1's 19 errors to probe 2's
match is the measurement that confirms the cause below.

## Cause 1 — the compare was hierarchy-asymmetric (all 19 errors)

**Class: flow setting.** The smoke LVS request omits
`options.flatten_layout: true`, which the pinned tool's own documented recipe
for the gate-level-verilog-on-FinFET route requires; `flatten_reference`
defaulting to true is the tool's behaviour, not something the flow chose.

The evidence chain, each link checkable:

1. `flow/smoke/run.sh:332-336` sets only `options.finfet_bulk`. It sets
   neither flatten option.
2. The record echoes `options.flatten_reference: true`,
   `options.flatten_layout: false`, and carries the matching
   `topology.flattened` warning: *"options.flatten_reference flattened the
   reference netlist before comparing: 13 circuit(s) were collapsed into 1
   top-level circuit(s), substituting every subcircuit-call instance in
   place…"*. Defaults confirmed against the pinned tool's own docs.
3. The reference became one flat `COUNTER` of 418 devices / 230 nets; the
   layout kept its hierarchy — `counter` holding **0 devices** and 47 nets
   with 18 logic-cell circuits beneath it (`counts` table above).
4. Every layout subcircuit therefore has no counterpart → the 18
   `side: "layout"` errors; the two top circuits cannot pair as circuits →
   the 1 `side: "both"` error. `details: null` on all 19 is what an
   unpaired-circuit finding carries at this level — no per-net or per-device
   detail exists because the compare never got past circuit pairing.
5. Probe 2 adds the two flatten options and the verdict flips to `match`
   with every device and net paired.

Fixing `run.sh` to set the recipe is deliberately out of scope here (issue
#98's Out of Scope; the flow change is a separate issue). Background for why
the recipe exists: klayout-tools
[#4514](https://github.com/2AMLogic/klayout-tools/issues/4514) (closed) — a
multi-cell stream vs a hierarchical reference only compares after flattening
both sides.

### The `$VAR1` variants are instances of cause 1, not a second cause

6 of the 18 unpaired layout circuits are `$VAR1` variants. KLayout's
extractor specializes a cell into `$VARn` masters when placed instances
differ in imposed connectivity (e.g. an interior rail split); the mechanism
is inferred from the names and was not traced. What is **measured** is the
compare-relevant part: the GDS instantiates distinct `$VAR1` masters for
exactly those 6 logic cell types (instance walk over
`counter.gds`: 17 `$VAR1` logic instances in total), the extracted netlist
carries them as their own circuits, and under probe 2's symmetric flattened
compare **they pair like every other circuit** — the `match` reports 418/418
devices with no `$VAR1`-specific finding. So they add no independent cause;
remove the asymmetry and they disappear with the rest.

### The top-cell name case is not causal

The request names the top cell `counter` on both sides
(`run.sh:288-289`), but the reference's SPICE form arrives upper-cased — the
record and probe 1 both echo `top: "counter"`, `reference_top: "COUNTER"`,
consistent with KLayout's SPICE reader normalizing circuit-name case. Closed
klayout-tools [#231](https://github.com/2AMLogic/klayout-tools/issues/231)
records that `klt lvs` pairs circuits by name, which is why the `side:
"both"` entry can name `{layout: "counter", reference: "COUNTER"}`: **klt did
pair the two tops** despite the case difference, and probe 2 matches with the
same inputs. The case difference is therefore cosmetic here; it explains the
odd-looking circuit names in the one `side: "both"` entry, not any of the 19
errors.

## Cause 2 — no diagnostic exists for this asymmetry (tool gap)

**Class: tool.** The pinned tool's `topology.hierarchy_mismatch` warning
(klayout-tools #4548) covers only *flat layout vs hierarchical reference with
`flatten_reference` unset*. The inverse — hierarchical layout vs a reference
the tool itself flattened by default — produced no structural diagnostic
here: just the 19 generic errors with `details: null`. Confirmed against the
pinned tool's source: `_hierarchy_mismatch_warnings` returns empty whenever
`flatten_reference` is set, and its shape check additionally requires the
layout side to be a single circuit — so the direction this route's default
produces is unreachable twice over. A caller hitting the default-on
`flatten_reference` with `flatten_layout` unset gets no hint that asymmetric
flattening is the cause.

Filed as klayout-tools
[#5756](https://github.com/2AMLogic/klayout-tools/issues/5756): *"lvs: no
hierarchy-asymmetry diagnostic for hierarchical layout vs reference flattened
by the default-on flatten_reference (inverse of #4548)"*. This is a
diagnostic gap, not a verdict gap — probe 2 shows the tool compares correctly
once told; it just does not tell the caller what to tell it.

## The 57 warnings, classed

- **36 `device.finfet_bulk_tied`** — expected and intended.
  `options.finfet_bulk nmos=VSS pmos=VDD` per decision 0005 (ASAP7 cells
  draw no taps), applied per layout circuit; every entry has
  `status: "joined"`. Class: **flow setting, deliberate and disclosed** — the
  bulk connectivity is a caller assertion, not geometry read from the layout.
  Not a defect. No tool issue.
- **18 `net.supply_fragmented`** — one per layout cell circuit, e.g. *"supply
  'VDD' spans 2 disconnected layout nets in circuit
  'AOI31xp33_ASAP7_75t_R'; connect the supply grid or configure
  options.supply_nets…"*. Class: **consequence of cell-internal geometry,
  disclosed** — a cell's rails are drawn as separate shapes that join only
  through the top-level power grid, which is outside the cell circuit.
  Measured: these 18 findings are **unchanged under probe 2's recipe** (the
  `match` run carries the same 18), so flattening does not resolve them and
  they are not a cause of the mismatch. For #31 this matters: even a
  `status: "match"` LVS on this route carries 18 supply-fragmentation
  warnings, and per the tool's own wording *"a signal-topology match does not
  verify power delivery"*. No tool issue (disclosure working as designed).
- **2 `reference.gate_level_pin_case_folded`** — `RESETN`→`RESETn` and
  `SETN`→`SETn` on `DFFASRHQNx1_ASAP7_75t_R`, 8 instances each, bound
  case-insensitively and disclosed as unambiguous. Class: **reference
  conversion, benign.** No tool issue.
- **1 `topology.flattened`** — the disclosure of the default-on reference
  flatten (cause 1, link 2). Class: **tool default, disclosed.** Probe 2
  carries two of these (both sides flattened explicitly). No tool issue.

## The 20 tapcells: in the layout, absent from the compare, disclosed nowhere

`par.json` reports `power.pdn: true`, `power.placed.tapcells: 20`,
`power.tapcell_master: TAPCELL_ASAP7_75t_R`. Measured, not inferred:

- An instance walk over `counter.gds` finds **exactly 20 tapcell instances**
  (`TAPCELL_ASAP7_75t_R` ×5, `…$VAR1` ×5, `…$VAR2` ×5, `…$VAR3` ×5) —
  matching `par.json` — plus 69 filler instances (28 `FILLER`, 24
  `FILLER$VAR1`, 5 `FILLERxp5`, 12 `FILLERxp5$VAR1`).
- The string `TAPCELL` appears in neither `counter_asbuilt.v` (the P&R
  Verilog writer emits no logic-free cells) nor `lvs.json`.
- An independent `klt extract` of the same GDS (klt 0.9.0, output outside the
  repo) shows where they go on this route: the extractor emits them as 8
  **device-less `.SUBCKT` stubs** (empty bodies — a tapcell/filler contains
  no transistor), alongside the 19 logic circuits. The LVS compare skips
  device-less circuits when pairing, so all 8 vanish without a finding —
  which is why the 27-circuit layout netlist produced exactly 19 unpaired
  errors and no mention of taps or fillers.
- The disclosure that should name them (`topology.power_only_pruned`) is
  scoped to the *non*-FinFET gate-level branch (`lvs.py` invokes
  `_prune_power_only_circuits` only when `reference.form` is
  gate-level-verilog **and** the deck is not FinFET), so on this route no
  power-only pruning is disclosed — there is no pruning step to disclose, the
  circuits are simply never compared.

**Bearing on #31:** the tapcells are the placed evidence that the rails are
tied (decision 0005's reason for `finfet_bulk`), but **nothing in `lvs.json`
exercises or discloses them** on this route — their rail-tie evidence lives
only in `par.json` (`power.pdn: true`, tapcell master named) and the
supply-spec ERC, never in the LVS report. Any #31 claim that cites the LVS
report for tapcell-backed power delivery would be citing a report that
structurally cannot see the tapcells.

## `power_connectivity`: why it says `unchecked`, and what that costs #31

The record's `power_connectivity.status` is **`"unchecked"`**
(`finding_count: 0`), with this reason, quoted verbatim:

> `reference.form is 'gate-level-verilog' on a FinFET layout.deck: each
> library cell was expanded to its transistor-level CDL body with its own
> power/ground pins, so supply connectivity takes part in the ordinary
> compare (a 'match' evidences it) and the stub-form power-pin check does not
> apply

This is **by construction, not by omission**: in the pinned tool's source,
the `reference.form == "gate-level-verilog" and finfet_layout` branch
(klayout-tools #4462/#4463's expanded-cell route) unconditionally overwrites
`power_connectivity` with that unchecked block — no code path on this route
can produce a power-connectivity verdict, let alone `"match"`. Confirmed
measured: probe 2's `match` run reports the same `unchecked` with the same
reason, even though its ordinary compare *did* exercise every expanded cell's
PG pins (418/418 devices matched).

Reading `manifests/design-evidence-tiers.md` (the document `klt signoff`
grades against):

- **Item 4 / #30** grades on `status == "match"` **and**
  `power_connectivity.status != "mismatch"` (lines 229-238). `"unchecked"`
  **satisfies** item 4 — the doc reads it as "does not apply here"
  (lines 249-252).
- **Item 11 / #31** requires that same report's `power_connectivity.status`
  to be `"match"`: *"`power_connectivity.status` is `"match"` —
  `"unchecked"` does **not** satisfy this item, unlike item 4 itself"*
  (lines 498-501).

So on the gate-level-verilog-on-FinFET route, `power_connectivity` is
**structurally always `unchecked`**, and item 11 is **not reachable through
the supported route the same document steers routed digital blocks through**.
The tier doc also enumerates when `unchecked` arises — *"every
`reference.form` other than `gate-level-verilog`, an explicit
`options.power_connectivity: false`, or a layout whose instances declare no
PG pins at all"* (lines 249-252) — and **this record matches none of those
three**: its form *is* `gate-level-verilog` (on a FinFET deck, which the
enumeration does not split out) and `options.power_connectivity` is `null`.

Filed as klayout-tools
[#5757](https://github.com/2AMLogic/klayout-tools/issues/5757): *"lvs:
power_connectivity can never report match for gate-level-verilog on a FinFET
deck, while the bundled tiers doc's power-delivery item requires match (and
its unchecked enumeration misses this case)"*. (Related but distinct:
[#4825](https://github.com/2AMLogic/klayout-tools/issues/4825), closed, asked
for the route itself pre-#4463; #5757 is the gap that remains after it.)

**For #31 this means, stated plainly:** re-running LVS on this route can
never produce the `power_connectivity: "match"` row item 11 asks for. Either
the tool gains an evaluator for expanded gate-level references, or item 11
needs a re-scoped formulation on evidence — the tier doc's own wording, not a
relaxed reading invented after the fact. That decision belongs to #31's
re-scope, not this file.

## What was deliberately not done

- **No change to `flow/smoke/run.sh`** — naming the cause (this file) and
  fixing the flow's LVS request are separate changes; the fix is also blocked
  upstream on the tool side (#5630, and the diagnostic gap #5756 would
  mislead the next caller the same way).
- **No new dated smoke record, no re-run of the smoke flow** — this issue
  produces an analysis, not a run of record; `flow/smoke/records/2026-11-05/`
  is byte-identical after this pass.
- **No LVS on the core** — that is #30; no re-scope of #30 or #31, and no
  edit to `manifests/design-evidence-tiers.md` — the item 11 consequence is
  stated above as a finding for those issues to act on.
- **The 549 DRC violations on this same layout** — classified separately in
  [`2026-11-05-drc.md`](2026-11-05-drc.md) (issue #97).
