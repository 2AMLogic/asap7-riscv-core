# Core LVS on the committed route (2026-11-28): what blocks T1 item 4, measured (issue #30)

T1 item 4 needs a `klt lvs` report on the routed core that reads `status:
match`, with `power_connectivity.status` not `mismatch`. No such report
exists, and this note records — each point measured on the committed
`layout/cve2_top.gds` (sha256 `abaf794b569e5956e5f4340e1ffc5ae5e6395b087ef7cf91f83591d3cec407e1`)
with the pinned tool — why it cannot exist yet, and what has to change before
it can. It lands the core LVS step, `flow/core/lvs.sh`, with its self-test;
it commits **no `lvs.json`**, because the step's reference is not available
in this session (see "Why there is no record" below). It changes no earlier
evidence.

**ASAP7 is a predictive PDK; nothing here is fabricated or measured.**
Every number below is a tool result against the pinned deck and the pinned
release. Nothing here is silicon.

**Citation convention:** as in [`2026-11-24-drc.md`](2026-11-24-drc.md):
references into scripts name the construct, never a bare line range.

## The step: `flow/core/lvs.sh`

`flow/core/lvs.sh <asap7-checkout> <routed-export-dir>` mirrors
`flow/core/drc.sh`: it reads the committed GDS as a blob at `HEAD`, refuses
unless the newest committed `par.json` pins those bytes in
`core_flow.gds.sha256`, runs the pinned `klt lvs` (deck `asap7`,
`provenance.deck.content_hash` `sha256:5c58a50e5f6a9099810b3fde37eaa8d93b0897653cb6597a831baac1f5ebee76`,
the pin of `spec/core.md` "DRC / LVS acceptance") with decision 0005's
`options.finfet_bulk {nmos: VSS, pmos: VDD}` and `flatten_layout`, and
records whatever the tool reports under `flow/core/records/<date>/`. A
mismatch is a recorded outcome; nothing is filtered. The request is the smoke
flow's `lvs` request heredoc shape (`flow/smoke/run.sh`, step 4), and it was
exercised against the real pinned tool on the committed counter layout
(`flow/smoke/records/2026-11-21/layout/`): `status: match`, 418/418 devices,
the report carrying every field the step validates (`environment.layout_sha256`,
`environment.reference_sha256`, `reference_conversion.form`,
`options.finfet_bulk`, `category_counts.device.finfet_bulk_tied`).

The step refuses, before anything runs, a report that would not be the
acceptance check: another deck hash, other input bytes, a reference that is
not `gate-level-verilog`, a bulk policy that is not echoed or not disclosed
as `device.finfet_bulk_tied`, or `status: inconclusive` (no verdict).
`flow/core/lvs_test.sh` pins all of it with a stubbed klt (82 cases).

## Why there is no record

The reference the step compares against is the **routed** gate-level
netlist, which `flow/core/par.sh --check --export <dir>` publishes once the
regenerated GDS compares byte-identical with the committed one. That bundle
does not exist yet: producing it needs a full core route, and confined to
two of this worker's shared cores the pinned route's detailed routing alone
ran about 24 minutes per iteration (measured: `[INFO DRT-0195]` 0th
iteration 25:21, 1st 23:34; the 2nd was underway when the run was stopped)
where the committed route needed twelve. The sanctioned route for that compute is the Spot run issue
#284 tracks, which publishes exactly this bundle. Until then the step has
nothing it accepts as a reference, and a record made from anything else
would not be the acceptance check.

## The reference has to be the routed netlist, not the item-1 netlist

The issue and its curation name the item-1 netlist
(`flow/core/records/2026-11-20/netlist.v`) as the reference. It cannot be:
place-and-route changes the cell population, so the routed layout is not the
synthesized netlist and no compare against it can match.

Measured: the instance census of the routed layout (`klt extract --deck
asap7`, klt 0.9.0, 511 s on this host: 31,105 nets, one circuit per placed
cell master) against `instance_counts_by_type` in
`flow/core/records/2026-11-20/synth.json`.

| | Instances | Masters | Devices |
|---|---:|---:|---:|
| Item-1 netlist (synth.json) | 29,785 | 59 | 205,342 (instances × CDL devices) |
| Routed layout (extracted) | 31,046 | 105 | 209,866 |
| Masters only in the routed layout | 1,596 | 46 | 6,480 |
| Masters in both, different count | net −335 | 24 | −1,956 |
| Masters in both, same count | 14,330 | 35 | — |

The 46 layout-only masters are drive-strength and pull-ratio variants of
synthesized cells (`BUFx2`…`BUFx12`, `INVx2`…`INVx6`, `INVxp67`,
`NAND2x1`, `NOR2x1`, `NOR4xp75`, `XNOR2x2`, …, 473 `BUFx4` and 218
`INVxp67` alone) plus the clock-gating inverter `CKINVDCx6p67`: the resizing
and buffering of `place`, `cts` and `route`. Tie cells are *not* among them
(`TIELOx1` 6,847 and `TIEHIx1` 2,497 on both sides), so this is sizing and
buffering, not constant insertion. Eight of the 46 are on the tool's
known-limitation list (next section).

This also retires the cause the 2026-11-24 builder note left open. The
parser refusal on the item-1 netlist (klayout-tools #7822, fixed by PR #7825
on unreleased main) is real, but it is not what stands between the core and a
match: with that netlist as the reference, 1,596 placed instances would have
no counterpart whatever the parser accepts. The tiers checklist's own
wording ("synthesized/routed gate-level netlist") is the one that fits a
routed block.

## Top-level pins: 200 of 263 labels sit on no conductor

`par.json` places 263 pins. The top cell carries their name labels on the
deck's pin-text layers: 200 on `M4.pin` (40/251), 61 on `M5.pin` (50/251),
2 on `M6.pin` (60/251, `VDD` and `VSS`). The pinned extractor's top circuit
has **62 pins**: 59 `M5` labels, `VDD`, `VSS` and the deck-synthesized
`vsubs`. **All 200 `M4` labels are lost**, and so are the
two `M5` labels `boot_addr_i[0]` and `boot_addr_i[1]`.

Both halves are geometry, measured in the top cell:

- A pin's `DEF PINS` rectangle is written on the pin *purpose* layer, not
  the conductor: for `boot_addr_i[10]`, a rectangle 0–0.084 µm ×
  48.960–48.984 µm on (40,251), with its label at the centre (0.042,
  48.972) µm. The routed `M4` wire on (40,0) runs from x = 0.060 µm, so it
  overlaps the pin rectangle for 24 nm but stops 18 nm short of the label.
  The deck reads `<metal>/251` as a *label* layer only
  (`metal_labels` in `klayout_tools/decks/asap7.py`), so the rectangle is
  nothing to it, and a label names a net only where a conductor covers its
  point.
- A label survives only where the wire happens to reach it:
  `instr_addr_o[8]` (extracted) has its `M5` wire ending exactly at the
  label's y. That is the luck of 59 pins; the 200 west-edge `M4` pins have
  no such luck.
- `boot_addr_i[0]` and `boot_addr_i[1]` have **no conductor within 0.2 µm**
  of their labels: they are the wrapper's two unused boot-address bits
  (`wire [1:0] unused_boot_addr` in `cve2_if_stage`), ports with nothing to
  route to.

This is klayout-tools #5700 ("place-and-route writes top-level DEF PINS
geometry to the layer map's pin purpose, which the extraction decks read as a
label layer only"), fixed by PR #6271 on 2026-11-18: the DEF→GDS merge now
draws each pin rectangle on the conductor too. The fix is **unreleased**
(v0.9.2 predates it) and it changes the GDS, so it reaches this block only
through the re-route at the bumped pin that issues #246 and #277 track.

Probe, pinned tool: a scratch copy of the committed GDS with the 377
pin-purpose rectangles also drawn on their conductor layers — the geometry
PR #6271 produces — extracts **262 pins**: the 62 above plus all 200 `M4`
labels, nothing lost. The two unused bits stay unpinned on klt 0.9.0, which
forms no net for a labelled conductor that touches no device (a minimal
fixture, two labelled conductor islands that touch no device: `pin_count 0`
on 0.9.0, `pin_count 2` on 0.9.2); from 0.9.2 they extract, once their
rectangle is on the conductor.

So the "61 layout pins versus 261 reference pins" of the earlier note is
attributed in full: 200 pins whose label is off the wire (fixed upstream,
needs the re-route) and 2 unused ports (fixed from 0.9.2, needs the same
re-route).

## 730 instances of 11 masters the tool lists as unsupported

Independent of pins and of any release, the routed layout instantiates
masters on the pinned tool's own known-limitation list
(`KNOWN_UNSUPPORTED_ASAP7_CELLS` in `klayout_tools/lvs_known_limits.py`;
docs "Pinned ASAP7 RVT corpus"). For these the library CDL and the drawn
transistor topology differ, and `klt lvs` "performs no stack normalisation":
each reports `mismatch`, "and they are not silently turned green". The list
is unchanged on upstream main today; PR #7045 (issue #6931, unreleased) only
adds a block-level disclosure.

Reproduced with the pinned tool on each master clipped from the pinned cell
GDS, compared against its own CDL `.SUBCKT` with the recorded options
(`finfet_bulk` + `flatten_layout`), control masters `NAND2xp33`,
`AOI21xp33`, `INVx1` each `match`:

| Master | Limitation | Instances (routed layout) | In item-1 netlist | Devices layout / CDL / matched | Per-instance errors |
|---|---|---:|---:|---|---|
| `AOI211xp5` | series-order | 273 | 275 | 8 / 8 / 2 | 6 `device.unmatched`, 2 `net.merged`, 2 `net.split` |
| `OAI221xp5` | series-order | 348 | 348 | 10 / 10 / 7 | 3 `device.unmatched`, 4 `topology` |
| `A2O1A1O1Ixp25` | series-order | 58 | 58 | 10 / 10 / 7 | 3 `device.unmatched`, 5 `topology` |
| `AOI21x1` | folded-stack | 27 | 0 | 8 / 6 / 2 | 10 `device.unmatched`, 3 `net.merged`, 4 `net.split` |
| `OAI21x1` | folded-stack | 9 | 0 | 8 / 6 / 0 | 11 `device.unmatched`, 17 `net.unmatched` |
| `AOI22x1` | folded-stack | 5 | 0 | 12 / 8 / 2 | 16 `device.unmatched`, 12 `net.unmatched` |
| `OAI22x1` | folded-stack | 1 | 0 | 12 / 8 / 2 | 14 `device.unmatched`, 12 `net.unmatched` |
| `NOR3x2` | folded-stack | 6 | 0 | 8 / 6 / 4 | 6 `device.unmatched`, 1 `net.merged`, 2 `net.split` |
| `NAND3x2`, `OR2x6`, `AND2x4` | folded-stack | 1 each | 0 | 8 / 6 / 4 | same as `NOR3x2` |
| **Total** | | **730** | 681 (679 still placed) | | ≥ 3,186 device errors |

Three of the eleven come from synthesis (681 instances in the item-1 netlist,
679 of them still placed); **eight exist only in the routed layout** (51
instances) — place-and-route's sizing chose them. Each run emits
the tool's own `topology.known_limitation` entry naming the master.

The consequence for item 4 is structural: under the ratified definition
(decision 0005, a transistor-level `match` against the pinned CDL) **no klt
release to date can report `match` on this layout**, because of these 730
instances alone. The count is a lower bound on the block mismatch, before
any cascade: the earlier as-built comparison's 25,910 `device.unmatched`
(builder note, scratch only) is consistent with the 730 instances plus the
pin loss of the previous section propagating through neighbouring cells, but
that split was not measured here — it needs the routed-netlist reference.

## `power_connectivity` is `unchecked` on the pinned release

On the FinFET gate-level route klt 0.9.0 hard-codes `power_connectivity:
unchecked` ("the stub-form pin-to-net check does not apply because the
expanded cells carry their own power pins"); measured again on the counter
run above. Item 4 accepts that, item 11 does not. klayout-tools #5757 (PR
#5925, merged 2026-11-17) derives `match` from the expanded-cell compare;
unreleased, after v0.9.2.

## What this means for T1 item 4

In order, each a precondition of the next:

1. **A klt release** carrying PR #6271 (pins on the conductor), #5925
   (`power_connectivity`) and #7045 (the block-level known-limitation
   disclosure) — the release klayout-tools #6930 tracks — then the pin bump
   of issue #246.
2. **The re-route at that pin** (issue #277): it is what puts the 263 pin
   rectangles on the conductor, and it publishes the routed-netlist bundle
   that `flow/core/lvs.sh` compares against (issue #284).
3. **A ruling on the eleven known-limitation masters.** Until it lands, the
   first core LVS record will read `mismatch` however clean the routing is.
   The options are a decision, not a builder's call, filed for the operator
   as #321: exclude the masters from synthesis *and* from
   place-and-route sizing and re-run items 1–3; accept item 4 as `unmet`
   with this attribution; or wait on an upstream compare mode
   (klayout-tools #8080). Note that the pinned `klt place-and-route` has no
   request-level dont-use list, so an exclusion reaches sizing only through
   a later release.

With 1 and 2 done, `flow/core/lvs.sh <asap7-checkout> <bundle>` writes the
first core `lvs.json`; item 4 reads `met` only if 3 is resolved by
exclusion.

## Reproduction

```
flow/core/lvs_test.sh                                     # the step's contract, no PDK needed
flow/core/par.sh <asap7-checkout> --check --export <dir>  # the routed-netlist bundle (a full route)
flow/core/lvs.sh <asap7-checkout> <dir>                   # the record
```

The measurements above, in scratch with the pinned build
(`uvx --from klayout-tools==0.9.0 …`):

- pin census and netlist census: `klt extract --deck asap7 --top
  cve2_rv32imc_wrapper` on the committed GDS, then a klayout walk of the
  top cell's (n,251) texts against the extracted `.SUBCKT` header, and the
  instance count per master against `synth.json`'s
  `instance_counts_by_type`;
- pin-conductor probe: the same extraction on a scratch copy with the
  pin-purpose rectangles copied onto (n,0);
- known-limitation masters: `klt clip --cell <master>` from the pinned cell
  GDS, then `klt lvs` with the `lvs` request heredoc shape of
  `flow/smoke/run.sh` against the pinned cell CDL.

## What was deliberately not done

- **No `lvs.json`.** The step refuses any reference but the routed netlist
  of the committed route, and that bundle was not produced in this session.
- **No compare against the item-1 netlist**, released or unreleased: the
  census shows it cannot match, so the result would be a mismatch that
  measures the reference, not the layout.
- **No edit to the netlist, the layout, the spec or a pin** to make a
  result look different, and no scratch probe output presented as a record.
- **No re-route and no change to the synthesis or sizing cell set**: both
  re-land items 1–3 and need the ruling named above.
